# 新規ゲーム導入（2026-10-31 神宮承認 TASK_ASSIGNMENT）

対象はこの導入で新しく開始したゲームだけ。既存セーブの初期化・移行・進行推定は行わない。

## 初期値と導線

初回起動とプレイ記録パネルの明示的な新規ゲームは、共通の`createNewGameHub()`を使う。未開封コンテナ10個、0c、機体なし、回路なし、弾薬・装甲・電力・ジャンクすべて0。4資源は既存の疎な在庫形式（省略も0）で保存する。初期支給は初期スナップショットの一部で、補充処理ではない。

HUBの短い案内から既存の未開封コンテナ→仕分→格納庫へ進む。既存の価格・抽選内容を用いて売買、作成、修復、装備、補給を行う。初回の中身保証・無料補給は追加しない。1×1不完全回路はジャンク2個＋6c。機体作成は既存どおり装甲300＋500c。

`INITIAL_HUB`は旧セーブの欠損値・既存の明示的なデモ初期化が参照する互換用テンプレートとして残す。通常の新規ゲームの初期値には使わない。検証シード・アルファ実験室は別の明示操作であり、通常の初期支給と混同しない。デモ初期化ボタンの表示も「デモ初期化」とする。

## 初出撃

新規導入の初出撃は、このゲームでジャンクから作成した1×1不完全回路が、修復済みの有効状態で、実際に出撃する隊長に装備されていることを要求する。既存の回路分類・修復状態判定を使う。機体のみ、未修復・未装備・別機体への装備では開始しない。

HUBの出撃URL生成とExploreの実際の`startSortie`で検証する。Invade・強制戦闘・直接URLも後者を通る。画面を開いただけでは完了にしない。開始時のnonce・隊長・回路IDをHUBへ保存し、既存のプレイログによる原子確定・失敗時の固定候補再試行へつなぐ。2回目以降の出撃条件や戦闘中の操作ゲートは変更しない。

新規導入は`starterCircuitGranted`と旧補填の完了印`ammoBatteryRepaired`を初期状態で設定し、さらに進行印がある場合は隊長の自動補完を拒否する。機体作成後やExplore再訪でも回路は無料付与しない。旧セーブの既存契約は今回の対象外。

## 初期コンテナと収穫0

出庫は開封完了ではない。出庫時は作業IDと初期分の個数を予約し、仕分結果の確定時だけ開封済み数・累計収穫へ反映する。預け・取消では加算しない。累計は資源在庫・所持金とは別に保持し、後から売買・消費しても変えない。

初期10個すべてを開封し、全4資源の累計収穫が0の場合だけ5,000,000cを一度付与する。同じ作業IDの再反映は無変更。専用演出は設けない。

Q1=A（神宮）：初期支給分を購入分と別バッチにする。初期分が残る間は残数以内で出庫し、仕分での追加も初期分の未出庫数まで。既に開封予約がある場合は同じ作業へ戻し、二重に出庫しない。

## 保存責務

`HubSnapshot.newGameIntro`は新規ゲーム初期スナップショットにのみ作る任意の追加フィールド。欠如する旧セーブに合成しない。版、初期開封済み数、累計収穫、付与済み印、作成1×1回路ID、処理中の開封予約、初出撃開始記録を保存する。回路・機体そのものの保存形式は変えない。

プレイログはこのHUB差分と仕分結果・初出撃スナップショットを記録する。IndexedDB確定前にゲームを進めない既存の遮断・再試行を利用し、価格や抽選結果を復元時に再計算しない。既存履歴は削除しない。

### 結果の受取

仕分完了時は固定の収穫を未受取キュー`results`へ保存し、初期進行と救済の条件を同じログ確定へ含める。格納庫への戻りは`introResultId`に対応する保存済み収穫だけを一度受け取る。URLの収穫を再計算・再加算しない。未開封で戻す`introCancelId`は一致する予約分だけを返し、開封数は増やさない。戻りトークンは既存の一度きり照合とログ確定の対象。初期バッチの「もう一度」やデモ切替を無効にし、支払済みの初期バッチを無料で再開封する経路を作らない。

格納庫の通常再訪でも未受取の初期バッチ結果を保存済みレシートから受け取る。戻りリンクを使わず移動した場合や別タブでも収穫が宙に浮かないようにし、未受取レシートの消去と在庫加算を同じ確定へ含める。消去済みIDの再適用はURLの収穫へフォールバックせず無変更となる。全レシートの履歴はプレイログへ残り、履歴は削除しない。新規作成機のバッテリーは既存契約どおり300/300、弾薬は0。初回専用の変更や追加補填はしない。

### 導入検証で再現した仕分入力の不具合

既存Sortはrootでpointer captureを行うが、タップ後のclickをセルで受ける前提だった。Chromiumではpointerupとclickがrootへ届くため、実タップでセルを選択できず、普通の収穫が成立しなかった。pointerupで既存のtap reducerへ渡し、互換clickとの二重処理を抑止する。マッチ・収穫・スワイプ判定の既存定数は変更しない。キーボード由来のclick（detail 0）は従来のセル操作経路を使用する。

## 検証の分離

通常経路の検証はデモ・シード・実験室を使わず、自然の仕分収穫の売却と既存の1×1作成・最低売価の取引（ジャンク2個を12cで買い、6cで作成、未修復25cで売却＝差額7c）で資金を整える。価格式は今回変更しない。収穫0の一度きり付与を使う検証は別の新規ゲームで行う。実物のスマートフォンと公開版操作は、ローカルChromiumの390×844操作と区別して記録する。

初期10個の開封後、この新規ゲームで購入した通常コンテナも同じ作業ID・固定レシートで扱う。初期分の個数は0、全体個数は`containerCount`として保存し、通常収穫は初期累計・救済判定へ含めない。同じ個数の別の有料バッチでもURLを区別し、前バッチの仕分状態を再利用しない。受取済みレシートは現在の未受取キューから除き、履歴はプレイログで保持する。旧セーブの既存開封経路は変更しない。

## 第三者の確認手順

1. HUBの「プレイ記録」から確認付きで新規ゲームを開始する。0c・機体/回路なし・4資源0・未開封10個を確認し、再読込しても同じであることを確認する。通常の既存セーブでは自動開始しない。
2. 「コンテナを開封する」から既存の出庫へ進む。未開封で格納庫へ戻した場合は在庫が戻り、開封済み数は進まない。初期分と購入分が混在する数量は出庫できない。
3. 通常の仕分操作で収穫し、格納庫で売買・作成する。回路作成はサイズ1×1を選ぶ。回路は未修復で生まれるため、Restoreで導通させてBypassを確定し、格納庫で隊長機へ装備する。機体作成・弾薬補給・充電の価格と方式は既存どおり。
4. 機体だけ、未修復、未装備、別機体への装備では初出撃を開始できない。Exploreを直接開いた場合・Invadeの強制戦闘でも同じ。出撃ボタンを押す前は初出撃記録がなく、開始確定後にnonce付きで記録される。
5. 別の新規ゲームで初期分4個→6個を一度もマッチせずに精製終了し、10個を使い切った時だけ5,000,000cを受け取る。収穫が1個でもあったゲームでは、後から残金や在庫を使い切っても発動しない。戻りURLの再読込でも資産は増えない。
6. 「プレイ記録」からJSONを書き出す。`scripts/verify-play-log-export.ts`へファイルを渡し、初期状態からの復元と最新確定状態の完全一致を確認する。旧履歴の初期状態を今回の初期値へ変換しない。

ローカル検証：`npm test`、全5本番ビルド。実操作は`verify-new-game-intro.cjs`（PC/390px・失敗再試行・通常/初期バッチ）と`verify-intro-economy.cjs`（救済金なしの実経済→初出撃）。ChromiumとPlaywright Coreが必要で、既存の検証スクリプトと同じく`PLAYWRIGHT_MODULE`でモジュールの場所を指定できる。これらは公開URL形式へのリクエストをローカルのdistへ振り向けて実行し、公開版へは書き込まない。

タップ補修は既存の`swipeMinPx`未満だけをtap reducerへ渡し、大きな斜め移動や盤外へのスワイプは従来どおり不成立とする。新しい閾値は追加しない。破損データや将来版の保存データが存在する場合も新規の空環境とみなさず、既存のバックアップ・読み取り専用の扱いを維持する。

保存された所有機のないExplore/Invadeの孤立した出撃用URLは、旧デモ機体・旧デモ資金で通常出撃を開始せず、格納庫へ案内する。旧チェックポイントの再開と明示的なDEBUG_FIXTUREは例外として既存どおり維持する。通常の開始関数にも所有セーブ不在の拒否を置く。既存の引渡しから途中履歴を合成しない#331の方針は変更しない。

初出撃の導入ガードは通常プレイの対象だけに適用する。`DEBUG_FIXTURE_ACTIVE`の隔離実験室ではこの新しいガードを適用せず、通常セーブをコピーした場合も任意の装備検証を続けられる。空の検証領域は通常の新規導入を自動付与しない。既存の検証用シード・デモ初期化も、UI表示とプレイ記録の`debug.*`操作名で通常開始と区別する。
