## 保存契約

HubSave v3に任意の`hub.fieldObjectIdentities`を加算する。旧セーブで欠損なら欠損のまま、残骸・盾・修復イベントは作らない。既存のUnit.id、機体instanceId、回路circuitId、lostMechsは変更しない。

```json
{
  "nextWreckId": "3",
  "nextShieldOrder": "2",
  "wrecks": { "wreck-record-key": { "wreckId": "2" } },
  "shields": {
    "shield-record-key": {
      "shieldId": "1",
      "sourceWreckId": "1",
      "sourceWreckIdInferred": false,
      "generationOrder": "1"
    }
  },
  "repairLogs": []
}
```

- 数字は正の10進文字列で保存。安全な整数の旧入力も読み取る。BigIntで比較・加算し、JSONにはBigIntを書かない。長期運用でNumberの精度上限によるID再利用を起こさないための技術上の形式。
- カウンターは同一セーブ内で共有。物体除去で巻き戻さない。セーブのコピー・古いバックアップ復元はそのデータのカウンターをそのまま継承し、外部時刻・別セーブとの一意性は要求しない。
- レコードキーは保存内で物体を参照するための安定キー。`{kind,key}`で参照し、ID修復でも同じレコードに解決する。将来の予約・装備はこの参照で接続する。`sourceWreckId`は歴史的な出自であり、現在の残骸への参照ではないため振り直さない。
- レコード内のHP・位置・進捗・回路情報などの追加プロパティは修復時も保持する。これらのゲーム上の意味や配置・所有状態のスキーマは後続で定義する。
- `registerWreckIdentity`は保存カウンターから割り当てる純粋関数。`shieldIdentityFromWreck`は**呼出側が剥離完了を確認した後だけ**使うID遷移で、残骸1レコードを取り除き、同じIDと新しい生成順の盾1レコードを作る。作業時間・射撃・予約・回路消費の実行処理は含まない。
- **現行フィールドの死亡処理へはまだ接続しない**。地面盾・戦場寿命・剥離処理が未実装のため。既存残骸を二重登録・消滅させず、次の剥離実装から基盤APIに接続する。

## 修復

1. 現存残骸と盾の最大個体IDを調べ、欠損／不足するnextWreckIdを最大+1（なしなら1）に修正。十分大きい値は維持。出自IDは現存個体IDの最大値計算に入れない。
2. 盾を生成順の古い順に確認。盾同士の同一IDは最古を保持し、他は保存カウンターから振り直す。同じ生成順の場合は保存順を保持する技術上の安定処理で、順位値は変更しない。
3. 残骸の重複IDを振り直す。盾と衝突すれば盾を維持。安定キーとペイロードは不変。
4. 盾の出自欠損は修復後の現在shieldIdで補完し、推定フラグを保存。有効な出自はそのまま。
5. 新たな修復だけを1イベントへ集約。UTC時刻・種別件数・対象キー・変更前後を保存し、severity=errorを次の赤色ログUIへ渡す。生成順カウンターも保存し、不足時はcounter修復に含める。
6. 正常化は冪等。再読込で新しい修復がなければイベントを増やさない。v3読込時は修復データとイベントを一緒に書き戻す。旧キーは変更せず、既存のv3移行経路で保存する。

物理的な順序が不明な盾（generationOrder欠損）やレコード構造の破損は最古を推測せず、既存の読込不能バックアップ経路へ回す。元テキストを残し、データを間引いて成功扱いにしない。将来版セーブは引き続き読取専用で、未知の形式でも上書きしない。

書込み拒否・容量不足では元セーブを維持し、修復済み状態はメモリー上だけで返し、`fieldIdentityRepairSaveFailed=true`を報告する。UI通知は後続。コピー通知・文字選択・スクロール・未読表示も後続であり、今回ログパネルは変更しない。
