# プロジェクト開発運用方針（オーケストレーション＆リポジトリ運用規約）

本ドキュメントは、プロジェクト全体の開発効率化および人間（ユーザー）のコンテキスト中継負担を解消するための運用方針・開発体制を定義したものです。

---

## 1. 背景と目的
従来の開発フローでは、人間が各モジュールやエージェント間のやり取りを中継（メッセンジャー役）しており、コンテキスト同期のオーバーヘッドおよびボトルネックが発生していました。  
これを解消するため、**「オーケストレーター型マルチエージェント体制」**へ移行し、人間は「要件の提示」と「最終承認・デプロイ判断」に専念する体制を確立します。

---

## 2. 開発体制と役割分担

### 2.1. 人間（プロダクトオーナー / レビュアー）
- 全体要件・仕様のインプット
- 各エージェントから上がってきた Pull Request (PR) のマージおよび最終デプロイ承認
- ※エージェント間のコードや文脈の中継作業（メッセンジャー役）は原則として行わない

### 2.2. 親ボット（GrokBot / オーケストレーター）
- プロジェクト全体のアーキテクチャ設計および進行管理
- 要求タスクのモジュール単位への分解・スコープ定義
- 各サブ開発エージェントへの作業指示・インターフェース調整
- サブエージェントが作成したコード／PRのレビューおよびマージ調整

### 2.3. サブ開発エージェント群（ワーカー）
- 指示された特定モジュール・ディレクトリに限定した実装およびテストの実施
- 担当モジュール以外のコードには原則介入しない（境界の維持）
- 作業完了時のPull Request作成および親ボットへの差分・完了報告

---

## 3. リポジトリ構成（モノレポ方針）

管理の複雑化およびバージョン不整合を防ぐため、**「単一リポジトリ（モノレポ構成）」**を採用します。

### 3.1. ディレクトリ構造規約
```text
my-project/
├── packages/
│   ├── shared/            # 共通インターフェース・型定義・共通スキーマ
│   ├── module-a/          # モジュールA（サブエージェントA担当）
│   └── module-b/          # モジュールB（サブエージェントB担当）
├── docs/                  # 設計書・仕様書
├── .github/               # CI/CDワークフロー等
└── README.md
```

### 3.2. モジュール境界の管理
- モジュール間で共通して利用する型やAPIスキーマは `packages/shared` で一元管理する。
- サブエージェントがインターフェース変更を要する場合は、まず `packages/shared` の変更案を親ボットに提示し、承認後に実装を進める。

---

## 4. Git・ブランチ運用ルール

1. **mainブランチの保護**
   - `main` ブランチへの直接プッシュは禁止。常にPRを経由する。
2. **ブランチ命名規則**
   - `feature/<module-name>-<task-name>`
   - `fix/<module-name>-<issue-name>`
3. **作業フロー**
   - 親ボットのタスク指示に基づき、該当ブランチを切る。
   - 実装・検証が完了したらPRを作成し、親ボットがレビューを行う。
   - 人間または親ボットが確認後、`main` にマージする。

---

## 5. デプロイ方針（.grok.me連携）
- GitHubの `main` ブランチをソースコードの信頼できる唯一の情報源（Single Source of Truth）とする。
- `main` ブランチへのマージをトリガーとし、GrokBuild経由で `.grok.me` 等のホスティング環境へ自動デプロイを行う。
