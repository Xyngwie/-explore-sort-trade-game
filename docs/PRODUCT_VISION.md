## 1. ひとことで

ディストピアの生活基盤ゲーム。戦闘は目的ではなく **障害**。薄い／敵の少ないエリアを探索して無事に帰る、も正当なプレイ。

---

## 2. ファンタジー

- **生業としてのサバイバル:** 資源を拾い集め、拠点で精製し、機体を直し、次の出撃へつなぐ。
- **戦闘は障害:** 殲滅やスコア稼ぎが主目標ではない。接触コスト・摩耗・弾薬・機体損失が「戦う理由を減らす」側に働く。
- **薄いエリアも有効:** 敵ライトなセクターを回り、コンテナを積んで帰るルートは第一級の正解。無理に前線へ突っ込む義務はない。
- **リスクは選ぶもの:** どこで漁るか（ルート／密度）をプレイヤーが決め、その結果として摩耗と収穫が付いてくる。

### 3.1 Module 1 — explore

- リアルタイムの有人ソート（出撃）。
- サルベージ成果と **機体摩耗** がセットで戻る。
- 僚機は方針で動く: **帯同 / 哨戒 / 回収 / 遊撃**（詳細は `EXPLORE_BEHAVIOR_V0`）。
- 「実入り」（コンテナ／yield の本体）はここに寄せる想定。
- **積載遅延＋仮設キャンプ（薄実装済）:** サルベージしたコンテナを運ぶと移動が遅くなる（`salvagedCount/capacity` → `BALANCE.cargoSpeedMulMin`）。プレイヤー任意の仮設ステージング／キャンプに預けて軽装探索し、後で取り上げて脱出へ運ぶ（詳細は `EXPLORE_BEHAVIOR_V0` §5.4）。

#### 3.1.1 僚機の学習と癖（未成熟な願望メモ）

> **ステータス:** 未実装・未着手・スケジュール外。受入条件でも実装チケットでもなく、まだ煮詰めていないビジョンメモ。

将来の Wingman は、AI が勝手に新しい分類を発明するのではなく、デザイナーがあらかじめ用意した **メトリック箱**（成功／失敗カウンター）を積み上げて学習する想定。例えば命中・撃破・被弾・接近中の成否など、ゲーム側が定義した軽量な指標だけを記録する。リプレイや大きな学習モデルを保存するのではなく、HubSave にも載せやすい小さな集計値に留める方向で考える（保存契約は [`HUB_SAVE_CONTRACT.md`](./HUB_SAVE_CONTRACT.md) を参照）。具体的な箱・重み・更新頻度は未決定。

この集計から、ロードアウトに左右されず強い一方で、行動の習慣を持つ **人間らしい癖** が見えてくるのが理想。たとえば「ゼロヒットで詰める（zero-hit closing）」癖が強く出ると、スナイパー機を実質的に近接機のように使うかもしれない。最初から `scout` や `armor` のような役割ラベルを与えるのではなく、まず実績／性能を観測し、後から役割の呼び名が立ち上がる設計を望む（役割解放の未成熟メモは [`RESTORE_V0.md`](./RESTORE_V0.md) および本書 §3.5 を参照）。

現在の戦闘スタブでは `heading == muzzle` のため、静止した敵を相手にヘリコプターのように旋回し続けられる。これはスタブとしては許容する。後段で機体の旋回速度や砲塔ラグを導入し、照準と機体姿勢を分離する余地を残す。

さらに先の社会的な広がりとして、エース敵が他のエースの学習プロフィールを写す、または他プレイヤーのエース僚機データを共有して「X の AI は怖い」と語られるようなコミュニティ上の味付けも考えられる。ただし、プロフィール共有・マルチプレイヤー・ソーシャル機能は明確に後回しであり、現行の設計や実装スケジュールには含めない。

### 3.2 Module 2 — sort

- 毎日触る精製レイヤ。薄利でも回数が効く。
- 契約語彙は `SORT_V2` / `YieldBag` を参照（本ビジョンは上書きしない）。
- **手触り:** **Zoo Keeper + アクティブ連鎖**。盤は開始時に埋まる。隣接スワップ（**上下左右**）→ 縦横 3+ マッチ消去 → **ゆっくり落下＋上補充**（そのあいだスワップ可）→ 自然連鎖。有効ピースが先で、尽きたらオジャマ（junk）だけが落ちて埋める。**Columns ではない。クラシック Panel de Pon のせり上げ圧・トップアウトでもない。** 経済・成果ルールは `SORT_V2`（`YieldBag` / `craftMultiplier` 等）のまま。
- **実装:** `packages/sort` はこの手触りで動作。試し方は [`SORT_V0.md`](./SORT_V0.md)。

### 3.4 Module 4 — invade / front（名称 TBD）

### 3.5 Module 5 — restore

- **ドラフト仕様（正）:** [`RESTORE_V0.md`](./RESTORE_V0.md) — 本節は願望の要約。`CircuitBoardState` 詳細は V0 を見る。
- `packages/restore`（ひな型）。Slitherlink 風の **回路復元**。
- 高価値なワンオフ成果。日常ループの薄利多売とは別軸。
- 状態例（願望）: Fully Awakened / Bypass / Offline。
- **タイマー圧なし。**
- 軽量セーブ案: `CircuitBoardState` 程度（おおよそ ~0.4KB）。

#### 設計哲学（願望 → ローカル厚みあり）

- 完全に解ける Slitherlink 盤は、稀な最上位の「true」コアとして扱う。
- 大半の盤は、意図的に矛盾や誤りを含むハズレ（**flawed substrate**）とする。
- それでもプレイヤーの手間は無駄にしない。部分解決を **Bypass** として性能向上につなげ、職人の腕前を感じられる余地を残す。
- この考え方は **Fully Awakened / Bypass / Offline** の成果状態に対応する。
- **ローカル厚み（`packages/restore`）:** 不完全基板生成・digit スコア・成果バナー・Perfect 刻印ロックスタブまで触れられる。出現率は Perfect injection レートに従う。詳細は [`RESTORE_V0.md`](./RESTORE_V0.md) §5.0。
- **未成熟な願望メモ（未実装）:** 回路の成果ランク（**Fully Awakened / Bypass**）に応じて、将来的に機体・部隊の兵種（**scout / armor / raid** など）を解放または役割切替できる案もある。ただし最善案として決定したものではなく、今は実装しない。

## 4. ループの指針（願望）

推奨の流れ（強制ではない）:

1. **任意で 4** — ルート／インテルを選ぶ（戦場密度・漁場の意思決定）
2. **1 で実入り** — 有人出撃でサルベージし、摩耗を払う
3. **2 → 3** — 精製し、拠点で修理・次備

短縮経路も正当:

- **ハブ（3）→ 直接 1** を許す（4 を毎回踏ませない）

### 報酬の分割（二重払い禁止）

| レイヤ | 渡してよいもの（願望） | 渡さない／控えめにするもの |
|---|---|---|
| Module 4 | ルート情報・インテル・希少ヒント | 本 salvage と同じコンテナ／yield の二重付与 |
| Module 1 | 実コンテナ・本 yield | （4 で既に渡した「本 salvage」の再払い） |

同じサルベージを 4 と 1 の両方で満額払わない。
