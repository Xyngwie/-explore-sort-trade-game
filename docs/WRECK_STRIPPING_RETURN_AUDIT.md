# #310 帰還精算の追加検証（2026-10-19）

## 指摘と再現

監査対象head `e096a7b` に対し、「Exploreの回収除外だけでなく、敵残骸の別精算経路でも再取得しないか」を検証した。

同じ敵を `enemyWrecks` と `wreckStripping.observations` の両方に含めるテストでは、**旧headでFAIL**。敵はsourceInstanceId=nullのため、剥離処理が回路を削除しても `recovered-<敵Unit ID>` の空の大破機が残った。通常プレイで矛盾データが自然発生することを確認した、という意味ではない。

## 修正

- `sortie-return.ts` は今回の観測とHUBの保存済み剥離履歴から消費機体IDを解決し、`applyEnemyWrecks` の前に回収行を除外する。
- 剥離の精算処理も、敵Unit IDから既存の受領ID `recovered-<Unit ID>` を解決し、既にある同機体と回路を除去する。回路0枚の場合も機体を残さない。
- 新しい剥離報告のない遅延した帰還データも、保存済み履歴で除外。未剥離の別個体は受領可能なまま。
- 旧航空支援の匿名大破機付与にも消費済み判定を追加。通常の敵IDと旧 `a:` IDの両方を調べ、結果snapshotが敵配列を省略していても除外する。
- 作業表がなくても、完了観測が残っていれば消費済みとして扱う。既存のID・所有・ゲームバランス仕様は変更しない。

## 自動回帰検証

修正後は以下PASS。

- 同じ敵の剥離＋回収情報が同時に存在する場合。
- 帰還URLでの同条件、空回路、既に受領済みの同一大破機と装備回路、同じsortieIdの再適用。
- 保存済み履歴しかない状態で、別のsortieIdから古い敵回収情報が届く場合。
- 未剥離の比較対象の受領は維持。
- 通常ID・`a:` IDの旧航空支援付与。敵配列と作業表を省略した結果snapshot相当でも付与されない。
