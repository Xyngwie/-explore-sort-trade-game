## 1. 基本原則

### 1.1 GitHub `main` をソース正本にする

- `main` にあるコードと契約文書を現在のソース・オブ・トゥルース (SoT) とする。
- GitHub Pages は `main` から生成される確認用プレビューであり、ソース正本ではない。
- 旧 `.grok.me` プロトタイプは、残存していても正本ではない。
- 実装とドキュメントが食い違う場合、まずコードと契約文書を調査し、意図を確認したうえでドキュメントを更新する。推測で仕様を変更しない。

### 1.2 人間は「何を作るか」と「最終的に入れるか」を決める

人間（プロダクトオーナー／レビュアー）は主に次を担当する。

- 要件、優先度、やらないことを決める
- プレイ結果や PR 差分を確認する
- 仕様変更、破壊的変更、公開判断、マージを承認する

コードの細かな編集やファイル間の機械的な同期は、可能な限りエージェント側で行う。

### 1.3 Codex はメインオーケストレーター、Cursor は高速実装レーン

2026-09-28 の神宮の決定により、役割を次のとおりとする。

- **Codex（ChatGPT、「チャッピー」）: メインオーケストレーター。** 要求整理、スコープ分割、契約への影響確認、PR 指示、進行状況（[`STATUS.md`](./STATUS.md)）の更新を担う。フルに使ってもトークン切れで止まりにくいため、進行状況と次の手を持つ役を任せる。オーケストレーターは止まってはならない。
- **Cursor（Grok Bot：参謀＋開発）: 高速実装・レビュー・デプロイ確認のレーン。** トークンがあるときに、ブランチでの実装、テスト・ビルド、PR 作成、レビュー、マージ後のデプロイ確認を行う。実装は最速だがトークン切れが最も早い。実装ワーカーが止まっても影響はその PR 1 本に限られる。短時間ならオーケストレーションを代行してよいが、止まる前に必ず進行状況をリポジトリ（`STATUS.md`）へ書き戻す。
- **人間（神宮）:** 要件、優先度、マージ判断を行う。
- **GeminiSpark:** ときどき第三者視点の UI 改善案を出す。提案は人間が手動で中継する。自動パイプラインではない（`.github/workflows/gemini-playtest.yml` は現在停止中・壊れた状態で、運用に組み込まれていない）。

軽微な調査や設計相談は、どちらか一方のチャットだけで完結してよい。

### 1.4 進行状況はリポジトリに置く（引き継ぎ）

進行状況はどのエージェントの記憶にも置かず、リポジトリに置く。これにより、どちらの側も数分で作業を再開できる。

- **作業を始める側（先に着手した方）** は、まず次を読む。
  1. [`docs/STATUS.md`](./STATUS.md)
  2. 開いている PR（`gh pr list`）
  3. `main` の最新デプロイ結果（`gh run list --workflow "Deploy Modules Preview" --branch main --limit 3`）
- **作業を止める側** は、止まる前に `docs/STATUS.md` を更新する（最終更新、最後にデプロイ成功した main コミット、開いている PR、次にやること、既知の問題）。
- `STATUS.md` と実際の状態（PR・Actions）が食い違う場合は、実際の状態を正とし、`STATUS.md` を直す。

## 3. 作業フロー

標準フロー:

1. **現状確認** — main のコード、関連 docs、直近の変更を読む。
2. **目的と受入条件を明確化** — 何を変えるか／何を変えないかを決める。
3. **影響範囲を確認** — shared 型、セーブ、ハンドオフ、UI、Pages などへの影響を調べる。
4. **専用ブランチを作成** — `feature/`、`fix/`、`docs/` など。
5. **実装／ドキュメント更新** — タスクのスコープ内だけを変更する。
6. **検証** — 少なくとも関連する typecheck / test / build を実行する。
7. **commit** — 目的が分かる単位で commit する。
8. **PR** — 変更概要、検証結果、未確認事項、契約変更の有無を記載する。
9. **レビュー** — 差分と実行結果を確認し、必要なら追加修正。
10. **マージ** — 人間または承認された運用主体が最終判断する。**1 本ずつマージし、そのマージコミットの `Deploy Modules Preview` が成功（緑）になったのを確認してから次をマージする**（[3.3](#33-マージは1本ずつデプロイ成功を確認してから次へ)）。

### 3.1 ドキュメントだけを更新する場合

コードを変更する必要がない場合でも、先に現在の実装を読んでから更新する。特に「実装済み／未実装」「正本」「次にやること」の記述は、コードと直近 PR の状態に合わせる。

### 3.2 仕様が不明な場合

- ビジョンから実装仕様を勝手に推定しない。
- 既存の V0/V2、契約文書、型、テスト、実装の順に確認する。
- 判断が必要な仕様差分は PR に明記し、マージ前に確認する。

### 3.3 マージは1本ずつ、デプロイ成功を確認してから次へ

原則: **PR を 1 本マージしたら、`main` 上のそのマージコミットに対する GitHub Actions `Deploy Modules Preview` が success になったのを確認してから、次の PR をマージする。**

背景:

- 2026-09-27 02:26〜09:41 JST、#114〜#123 を続けてマージする間、Pages デプロイが失敗し続けていた。Explore のビルドが、`coverMovement.ts` が `math.ts` から `dot` を import しているのに `math.ts` がもう `dot` を export していない、という理由で壊れていた。`df1689f` で `dot` を戻すまで、公開プレビューは古いままだった。
- 2026-09-26 07:21〜08:14 JST にも同様の短い失敗の連続があった（#105 で修正）。

確認方法:

```bash
gh run list --workflow "Deploy Modules Preview" --branch main --limit 3
```

または GitHub の Actions ページで `Deploy Modules Preview` を開き、該当マージコミットの run が緑であることを確認する。run の head SHA がマージコミットと一致していることも見る。

失敗（赤）だった場合:

1. 以降のマージを止める。
2. 失敗ログから原因を特定し、ビルド修正だけを行う PR を 1 本作って先にマージする（fix forward）。
3. その修正のデプロイが緑になってから、通常のマージを再開する。
4. `STATUS.md` の「最後にデプロイ成功した main コミット」「既知の問題」を更新する。

積み重ねた PR（stacked PR）は下から順にマージし、それぞれ前のデプロイが緑になってから次へ進む。

## 4. ブランチと PR

基本形:

```text
feature/<module>-<task>
fix/<module>-<issue>
docs/<task>
```

`main` への直接変更は避け、PR を基本経路とする。

PR 本文には最低限次を含める:

- 何を変更したか
- なぜ変更したか
- 変更しなかった範囲
- 実行した検証コマンドと結果
- 仕様／契約／セーブへの影響
- 未確認事項、既知の制限

## 5. 契約変更の扱い

次の変更は通常の UI 文言修正より慎重に扱う。

- `packages/shared` の公開型・ハンドオフキー
- HubSave / セーブ形式
- Module 間の I/O
- 経済値・Yield の意味
- Pages の公開経路
- 外部 URL や origin をまたぐ連携

契約を変更する場合は、実装と同じ PR に契約文書の更新を含め、互換性と移行方法を説明する。

CTA の文言統一など、契約キーを変更しない UI コピー変更は、契約変更と混同しない。

## 6. 検証

リポジトリ全体の基本確認:

```bash
npm install
npm run typecheck
npm test
```

UI を変更した場合は、該当モジュールの build も確認する。

```bash
npm run build:explore
npm run build:sort
npm run build:trade
npm run build:invade
npm run build:restore
```

変更範囲に応じて必要なコマンドだけを実行してよいが、PR 本文には実行した範囲を明記する。

## 7. やらないこと

- 実装されていない `PRODUCT_VISION` の願望を現在仕様として実装しない。
- 契約を確認せずにモジュール境界を変更しない。
- 無関係なリファクタリングをタスクへ混ぜない。
- Pages の表示だけを見てソースを変更するのではなく、まず `packages/*` と契約文書を確認する。
- PR を作らずに `main` へ大きな変更を直接投入しない。

## 8. 将来の拡張

必要になった場合にのみ、次を追加する。

- CI による typecheck / test / build の自動ゲート
- Pages デプロイの自動確認
- PR テンプレート／チェックリスト
- モジュールごとの受入テスト強化

これらは現行ゲーム仕様とは別の開発基盤改善として扱う。

## 9. 人間への次アクションを残して会話を止めない

開発エージェントは、調査結果・分析結果を提示しただけで作業を終了してはならない。

### 9.1 原則

調査・実装の各段階では、**次に神宮が何をすれば工程が進むのか**を明示する。神宮がPCを持たず、スマートフォンで実機確認を行う前提を考慮し、エージェント側で可能な作業は先に進め、神宮側でしかできない確認・操作だけを具体的に切り出す。

### 9.2 次アクションの種類

状況に応じて、次のいずれかを具体的に要求する。

- **説明を求める:** 仕様・意図・優先順位など、神宮の判断が必要な事項を質問する。
- **テストプレイを求める:** GitHub Pages 等へ反映した後、神宮のスマートフォンで確認してほしい操作・画面・期待結果を具体的に示す。
- **スクリーンショット／ログを求める:** エージェントから確認できない表示・挙動について、必要な画面やログを指定して送ってもらう。
- **権限・接続設定を求める:** GitHub、外部サービス、API 等へのアクセスが不足している場合、必要な権限や設定を特定し、神宮が行う操作を具体的に案内する。不要なAPIキーや権限を要求しない。
- **追加作業を宣言する:** 神宮側の入力が不要な場合は、次の調査・実装・PR作成などをエージェント側でそのまま進める。

### 9.3 「進めて」「はい」だけで終わらせない

「調査します」「原因を特定します」「結果を報告します」だけで会話を終了しない。調査後は、次の確認・実装・権限取得・テストのいずれかに必ず接続する。

神宮から追加情報を求める場合も、単に「確認してください」と言わず、**何を、どこで、どの状態ならどう判断するか**まで指定する。

### 9.4 開発工程を途切れさせない

標準的には次の流れを意識する。

```text
現状調査
  ↓
原因／変更範囲の特定
  ↓
必要なら神宮へ具体的な確認・権限・テストを依頼
  ↓
実装／ドキュメント更新
  ↓
PR
  ↓
Actions / CI / コンフリクト確認
  ↓
レビュー
  ↓
マージ
  ↓
Pages等のデプロイ確認
  ↓
神宮がスマートフォンでテストプレイ
  ↓
結果を受けて次の工程へ
```

PCなしで神宮自身が確認できないものを「確認済み」と扱わない。逆に、GitHub上でエージェントが確認できる事項を神宮に丸投げしない。
