**ステータス:** 採用（2026-09-16）  
**改訂理由:** 原案のオーケストレーション方針を維持しつつ、現行制約（GrokBuild 分割プレビュー、GitHub/Cloud Agents の制限、URLアダプタ運用、45MB統合トリガー）に合わせて段階適用できるようにした。

## 1. 背景と目的

従来フローでは、人間が各モジュール／エージェント間の文脈を中継するメッセンジャーになり、同期コストとボトルネックが発生していた。

目的:
- **オーケストレーター型マルチエージェント**へ移行する
- 人間は **要件提示** と **最終承認（マージ／公開判断）** に寄せる
- エージェント間のコード・文脈の中継を人間が担わない

---

## 2. 役割分担

### 2.1 人間（プロダクトオーナー／レビュアー）

やる:
- 全体要件・優先度・「やらないこと」の提示
- 上がってきた結果の確認（プレイ／スクショ／PR）
- **最終デプロイ／再公開の承認**（移行完了までは .grok.me 再公開ボタンが人間側に残る場合あり）

やらない（原則）:
- エージェント同士の文面・ZIP・差分のメッセンジャー
- モジュール間の受け渡しキーの手作業コピペ中継（親ボットが契約と指示に落とす）

### 2.2 親ボット「参謀」（オーケストレーター）

- アーキテクチャと進行管理
- 要求のモジュール単位への分解・スコープ定義
- 契約ドキュメント（型・セーブ・ハンドオフ）の維持
- サブ（開発／Build指示文）への作業指示とレビュー
- 人間への上げは **方針・破壊的変更・課金／権限・マージ判断** に限定

### 2.3 サブ開発エージェント「開発」（ワーカー）

- 指示されたモジュール／ディレクトリに限定した実装・テスト
- 担当外コードには原則介入しない
- 完了時は差分要約を親へ報告（将来は PR 作成）

### 2.4 Grok Build（実装プレビュー環境）

移行期間中の **実行プレビュー生成器**。  
チャット指示でモジュールを改修・公開できるが、**ソースの長期正本にはしない**（§5）。

---

## 3. 現行制約（この規約が前提にするもの）

| 制約 | 運用上の意味 |
|---|---|
| モジュールは当面別 .grok.me（URLアダプタで接続） | 「アプリ統合」と「リポジトリ統合」を分離する |
| ZIP が約 45MB 超で参謀へ添付困難 | その時点でアプリ統合を検討（既存決定） |
| Cloud Agents は Pro が必要な場合がある | 親はローカル／ZIP／開発エージェント等の代替経路を選ぶ |
| GrokBuild → GitHub Push が不安定なことがある | Export失敗時は ZIP／手動。正本移行は段階的 |
| 別オリジンでは localStorage 非共有 | セーブは拠点（Module 3）のみ（`HUB_SAVE_CONTRACT`） |

---

## 4. 段階ロードマップ

### Phase 0 — いま（採用直後）

- 本規約を正本とする
- 実行は 3 モジュール＋URLアダプタ
- 参謀が Build 向け指示文を書き、人間は **要件＋公開ボタン** に寄せる
- 契約類は `docs/` および既存 `modules/*.md` に集約

### Phase 1 — モノレポ骨格（ソース正本の受け皿）

```text
wreckline-game/          # リポ名は任意
├── packages/
│   ├── shared/          # 型・ハンドオフ契約・セーブスキーマ
│   ├── wreckline/       # Module 1
│   ├── athanor/         # Module 2
│   └── base-hub/        # Module 3
├── docs/
│   ├── ORCHESTRATION.md # 本ファイル
│   └── ...
├── .github/             # 将来 CI
└── README.md
```

- まずは **箱と docs／shared の型** まででよい（完全移行は後）
- サブは `packages/<module>/` のみ変更。`shared` 変更は親の承認後

### Phase 2 — Git 運用の本格化

- `main` 直接push禁止、PR必須
- ブランチ: `feature/<module>-<task>` / `fix/<module>-<issue>`
- 親がレビュー、人間または親がマージ承認

### Phase 3 — デプロイ自動化

- `main` = ソースの Single Source of Truth
- マージをトリガーに .grok.me（または後継ホスト）へ反映
- これが安定するまで、人間の「再公開」をチェックリストに残す

### Phase 4 — アプリ統合（任意・トリガー付き）

- 単一オリジン化、共通ストア、URLアダプタ退役
- トリガー例: ZIPが参謀添付上限を超える／セーブや受け渡し負債が肥大化

---

## 5. 正本（Source of Truth）ルール

### 移行完了前（Phase 0–2）

| 対象 | 正本 | 備考 |
|---|---|---|
| 設計・契約 | 本リポ／参谋 docs | ハンドオフ・セーブ契約 |
| 実行プレビュー | 各 .grok.me | プレイ確認用 |
| ソース | **目標は GitHub モノレポ** | 未同期の間は Build 改修後に Export/ZIP で参謀へ |

**公開漏れ防止（必須）:**  
Build で直したら、人間または親のチェックリストで「再公開したか」を確認する。未公開のまま次モジュールを触らない。

### 移行完了後（Phase 3+）

- GitHub `main` のみがソース正本
- .grok.me はデプロイ成果物

### Module 1（explore）正本メモ（2026-09-17）

- **SoT:** `packages/explore` + `docs/EXPLORE_BEHAVIOR_V0.md` / `docs/EXPLORE_IO_V2.md`
- 旧 Module1 `.grok.me` は **退役／練習用**。プレイ意図の参照のみ可。ビルド・URL 同期を正本経路にしない
- sort / trade は移行期間中もプレビュー URL を併記してよい


---

## 6. モジュール境界と shared

- 共通型・クエリ契約・セーブスキーマは `packages/shared`（または移行前は docs＋単一の型ファイル）で一元管理
- 例: `PlayerExpeditionState`、ハンドオフクエリ、`HubSaveV1`
- サブが境界変更したい場合: **先に shared／契約の変更案を親へ** → 承認後に実装

担当目安:

| パッケージ | 担当 |
|---|---|
| `shared` | 親が定義、変更は親承認 |
| `wreckline` | 開発 or Build（親指示） |
| `athanor` | 同上 |
| `base-hub` | 同上（セーブ実装含む） |

---

## 7. Git・ブランチ（Phase 2 以降で全面適用）

1. `main` 保護・直接push禁止  
2. `feature/<module>-<task>` / `fix/<module>-<issue>`  
3. 親の指示 → ブランチ → 実装 → PR → 親レビュー → 人間または親がマージ  

Phase 0–1 では、同等の「指示 → 差分報告 → 親確認 → 人間が公開」で代替してよい。

---

## 8. コミュニケーション規約

- 人間 → 親: 要件・優先度・承認／却下
- 親 → サブ／Build: スコープ付き指示（受入条件つき）
- サブ → 親: 完了報告・差分・リスク（人間へ生ログを浴びせない）
- モジュール間の「相手モジュールを直して」は親が契約と指示に分解する

---

## 9. やらないこと（当面）

- メッセンジャーとしての人間中継の常態化
- GAS をゲーム状態の本線DBにすること
- 契約なしの境界変更
- アプリ統合をトリガー前に強行すること
- 未公開プレビューを「完了」扱いすること
