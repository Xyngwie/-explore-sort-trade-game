## 理念

第1段階は、全部のゲームの骨組みになる要素をまず全部並べること。これは概ねできている。

第2段階は、それを canvas に載せるときに整えることだった。意図が伝わりきらず、並べた形のまま canvas へ載せてしまった。

本来あるべき形は、ツリー構造の操作系を少ない選択肢のパレットに組み直すことである。見た目の整理ではなく、一度に見せる次の行動を少なくすること。売買・機体・回路・出撃の実作業を HUB に再集結させない。

神宮の HUB 例示は分類の見本である。全部のゲーム内容について、パレットとそこにあるべき機能を神宮が全て例示する必要はない。以降の枝は、この文書の分類規則に従って実装側が分類し、処理する。

## パレットの原則

1. パレットとは、いまいる場所で次に選ぶ行動を少数だけ並べた画面である。見た目の整理ではなく、ツリー構造の操作系を組み直すこと。
2. 1枚に置くのは、現在地の情報表示（必要なら）と、次の行動を選ぶものだけ。
3. 次の行動が複数あるときは、その選択だけの枚を1枚作り、各行動の実際の作業は子の枚へ送る。選択枚に商品一覧・修理・装備などを埋め込まない。
4. 実作業枚はその作業だけ。買う・売るの商品リストと数量・確定、SORTゲーム、出撃中の explore など、作業に必要な操作は一緒に置いてよい。異なる作業のメニューは混ぜない。
5. 戻ると親の枚へ。共用作業は入ってきた枝を親とし、その枝へ戻す。パンくず・戻るは1段だけ。HUB 直帰は通常の戻ると区別する。
6. 今まで1枚に込めていたものを、同じ粒度で全部展開する。別機能の折りたたみ・タブの詰め込みで、巨大な DOCK をそのまま残さない。
7. ここでいう1枚は、同じアプリ・同じ canvas 内で切り替わる論理画面。別 HTML ページや新しい保存形式を増やす指示ではない。全画面の外枠と必要時のパネル内スクロールは維持する。
8. 神宮が例示していない枝も同じ規則で分類する。残りのパレットを神宮に全て書いてもらってから着手する前提にしない。

図や表の ID はこの文書内の参照名であり、新しい URL・保存キーの決定ではない。見出し・並び順・コピー・数値は、例示と既存決定を除き仮案。ゲームルールを変える決定権はこの文書にない。

## 分類の仕方

全部のゲーム内容について、パレットとそこにあるべき機能を神宮が全て例示する必要はない。実装側は、現行の骨組み要素を次の規則で分類し、処理する。

1. 対象は現行の骨組み要素だけ。新しい遊び、新しい取引対象、新しい確認や数値を発明しない。
2. ある場所に次の行動が複数あるなら、選択パレットにする。各行動の実作業は子のパレットへ送る。選択パレットに商品一覧や修理、装備の作業を埋め込まない。
3. 実作業パレットには、その作業に必要な操作だけを置く。数量を決めて買う、SORTの盤、出撃中の操作などは一緒でよい。別の作業の入口は混ぜない。
4. 同じ実作業へ複数の入口があるときは、実作業パレットは1つだけ作り、入ってきた枝へ戻す。売買から行く機体購入と、整備から行く機体購入は別実装にしない。
5. 確認、一時停止、開始画面、検証用の欄は通常のパレットツリーに入れない。既存の確認がある作業から確認を外さない。
6. 分類に迷ったら、神宮の HUB 例示と同じ粒度かを見る。1枚に複数の作業があるなら分ける。1操作ごとに枚を増やしすぎるなら、同じ実作業へまとめる。
7. 神宮に聞くのは、この規則だけでは決まらない細部だけ。残りのパレットを一覧してほしい、と求めない。
